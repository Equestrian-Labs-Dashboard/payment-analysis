# Shopify Payment Methods Analysis

Analytics tool for **Equestrian Labs, Inc.** (brands: **CORRO** and **CAVALI**) that answers the
question the business asked for:

> Which payment methods do customers use, how often, what % of transactions/revenue each one
> represents, and what are the Top 3 payment methods?

It pulls real order + transaction data from the **Shopify Admin REST API** (Orders API *and*
Transactions API — Orders alone is not enough, because Shopify does not reliably expose the real
gateway/payment method on the order object itself), computes the KPIs requested, and produces:

1. **`Shopify_Payment_Methods_Analysis.xlsx`** — the deliverable workbook, with the exact tabs
   requested:
   - `Executive Summary`
   - `Payment Method Summary`
   - `Transaction Detail`
   - `Payment Providers`
   - `CORRO Analysis`
   - `CAVALI Analysis`
2. **`dashboard/data/report-summary.json`** — the same numbers, consumed by the included web
   dashboard (`dashboard/index.html`), styled to match the existing Corro/Cavali Performance
   dashboard.

## Why Orders API + Transactions API

The Orders API tells you *that* an order was paid. It does not reliably tell you *how* — Shopify
often groups Shopify Payments, gift cards, and third-party gateways under a single
`payment_gateway_names` string, and that string does not include per-transaction status, the real
transaction ID, or (for multi-transaction orders — partial refunds, retried payments, split
payments) the individual methods used.

The **Transactions API** (`GET /orders/{order_id}/transactions.json`) returns each transaction on
the order individually, with `gateway`, `kind` (`sale`, `capture`, `refund`, `void`, `authorization`),
`status` (`success`, `failure`, `pending`, `error`), and `id`. This project joins that data back to
the parent order to build one row per transaction, which is the only way to avoid Shopify's
gateway-name grouping and get an accurate count per payment method.

## Project layout

```
shopify-payment-analysis/
├── src/
│   ├── config.js              Env/config loader (per-brand store + token)
│   ├── shopifyClient.js       Orders API + Transactions API client (pagination, rate limiting)
│   ├── paymentMethodMapper.js Normalizes raw gateway strings into display names
│   ├── dataProcessor.js       Joins orders + transactions, computes every KPI in the spec
│   ├── reportGenerator.js     Builds the 6-tab .xlsx with ExcelJS
│   └── index.js               CLI entry point
├── dashboard/
│   ├── index.html             Dashboard UI (matches the existing Corro Performance look)
│   ├── styles.css
│   ├── app.js                 Loads dashboard/data/report-summary.json and renders it
│   ├── assets/corro_logo.png
│   └── data/report-summary.json   (generated by `npm run report`, or use the sample)
├── sample-data/
│   └── report-summary.sample.json  Realistic mock data so the dashboard works with no API keys
├── .env.example
├── package.json
└── README.md
```

## Setup

```bash
npm install
cp .env.example .env
# fill in .env with each brand's Shopify store domain + Admin API access token
```

Required scopes on the Shopify Admin API access token: `read_orders`.

### `.env`

```
SHOPIFY_API_VERSION=2024-10

SHOPIFY_CORRO_STORE=corro-store.myshopify.com
SHOPIFY_CORRO_TOKEN=shpat_xxxxxxxxxxxxxxxxxxxxxxxx

SHOPIFY_CAVALI_STORE=cavali-store.myshopify.com
SHOPIFY_CAVALI_TOKEN=shpat_xxxxxxxxxxxxxxxxxxxxxxxx

# Optional — defaults to "last 3 full months" (the Q3-style window Ceci asked for)
REPORT_DATE_FROM=
REPORT_DATE_TO=
```

## Run it

```bash
# Generates Shopify_Payment_Methods_Analysis.xlsx in ./output
# and dashboard/data/report-summary.json for the web dashboard
npm run report

# last 3 full months is the default; override with explicit dates:
npm run report -- --from=2026-07-01 --to=2026-09-21
```

## View the dashboard

The dashboard is a static site — no build step.

```bash
npm run dashboard
# open http://localhost:4173
```

It reads `dashboard/data/report-summary.json`. Until you run `npm run report` against a real
store, it falls back to `sample-data/report-summary.sample.json` so the UI can be reviewed and
pushed to GitHub Pages immediately.

## Publishing to GitHub

```bash
git init
git add .
git commit -m "Shopify Payment Methods Analysis — CORRO & CAVALI"
git branch -M main
git remote add origin https://github.com/<your-org>/shopify-payment-analysis.git
git push -u origin main
```

A GitHub Actions workflow is included at `.github/workflows/generate-report.yml` — it can be
triggered manually or scheduled (e.g. daily/weekly) to regenerate the `.xlsx` and commit the
refreshed `dashboard/data/report-summary.json`, so the dashboard (deployable to GitHub Pages)
always reflects the latest window.

## Data dictionary (what the spec asked for → where it lives)

| Requested field | Source | Where computed |
|---|---|---|
| Company | Config (CORRO / CAVALI) | `src/config.js` |
| Order ID, Order Date, Created At, Financial Status, Fulfillment Status, Currency | Orders API | `src/shopifyClient.js` → `src/dataProcessor.js` |
| Payment Method, Payment Gateway, Transaction ID, Transaction Status, Transaction Date | Transactions API | `src/shopifyClient.js` → `src/paymentMethodMapper.js` |
| Subtotal, Discount Amount, Shipping Amount, Tax Amount, Total Order Value, Refund Amount, Net Revenue | Orders API | `src/dataProcessor.js` |
| Customer ID, Customer Type (New/Returning), Country, Email | Orders API (`customer`, `orders_count`) | `src/dataProcessor.js` — kept for internal analysis, not shown on the dashboard |
| Top 3 Payment Methods | Computed | `src/dataProcessor.js::computeTopPaymentMethods` |
| Available vs. Used providers | Config allow-list vs. observed gateways | `src/dataProcessor.js::computeProviderComparison` |
